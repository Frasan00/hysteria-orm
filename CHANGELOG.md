# Changelog

All notable changes to this project are documented in this file starting from 12.0.0. Version 11.x and earlier history is not tracked here.

## [12.4.0] - 2026-10-08

### Features

- **Multi-table writes on MySQL and MariaDB.** `innerJoin(...)` and the other joins now chain onto `update` and `delete` on MySQL and MariaDB, rendering `UPDATE <table> INNER JOIN ... SET ...` and `DELETE <target> FROM <table> INNER JOIN ... WHERE ...`. Every other dialect still throws `JOIN_NOT_SUPPORTED_ON_WRITE`. The joins are rendered between the table and the `SET` clause, which is where MySQL expects them, and a join-free statement is unchanged.
- **`updateFrom(source)` on PostgreSQL, CockroachDB, and MSSQL.** Sets the source a correlated `UPDATE` reads from, taking a table name or a callback that builds one, and renders `UPDATE ... FROM ...`. MySQL, MariaDB, and SQLite throw `UPDATE_FROM_NOT_SUPPORTED`.
- **`deleteUsing(source)` on PostgreSQL and CockroachDB.** Renders `DELETE FROM ... USING ...` so a delete can read another table. Named `deleteUsing` because `using(...columns)` already means `JOIN ... USING`. MySQL, MariaDB, MSSQL, and SQLite throw `DELETE_USING_NOT_SUPPORTED`.
- **Raw and named-constraint `onConflict()` targets.** `onConflict(sql.rawStatement("..."))` emits the predicate verbatim on PostgreSQL, CockroachDB, and SQLite, and `onConflict({ constraint: "users_email_key" })` emits `ON CONFLICT ON CONSTRAINT <name>` on PostgreSQL and CockroachDB. Both bypass column-name mangling, so a partial-index predicate survives intact.
- **`merge({ where })` on PostgreSQL and SQLite.** The `DO UPDATE SET` half can carry its own predicate, so an upsert can update a row conditionally. MySQL, MariaDB, and MSSQL throw `MERGE_WHERE_NOT_SUPPORTED`.
- **`update(key, value)`.** The two-argument form is shorthand for `update({ [key]: value })`, on both `sql.from(Model)` and `sql.from("table")`.
- **`batchInsert(rows, { chunkSize, returning })`.** Slices the rows and runs one `insertMany` per slice, so a large payload does not exceed the driver's parameter or packet limits. It resolves to the returned columns, or to the number of rows inserted when `returning` is omitted. The default chunk size is 500, and a non-positive one throws `INVALID_BATCH_SIZE`. The slices are separate statements, so wrap the call in `sql.transaction(...)` when the batch has to be all or nothing. SQLite caps a statement at 32766 bound variables, so keep `chunkSize` small enough for the widest row.
- **Grouped negation with `whereNot(cb)`.** A callback is negated as a whole, rendering `NOT (...)`, so `whereNot` no longer needs the group restated as separate negated predicates. The two-argument subquery form is unchanged.
- **Object-shorthand `where`.** `where({ status: "active" })`, `where({ age: { op: ">", value: 18 } })`, and `{ $and: [...] }` / `{ $or: [...] }` are accepted on `where`, `andWhere`, and `orWhere`. A bare value compares with `=`, an `{ op, value }` pair takes any binary operator, and a `null` value becomes `is null`. The operator lives on the value rather than on the key, which keeps a single-key object unambiguous and matches what `find()` and `upsert()` already accepted.
- **Multi-column tuple `IN`.** `whereIn(["id", "name"], [[1, "a"], [2, "b"]])` compares column tuples, with the `and`/`or` and negated variants alongside it. Each column is quoted on its own. MSSQL has no row constructors, so it expands every tuple into an equality group joined by `OR`. An empty column list throws `WHERE_TUPLE_COLUMNS_REQUIRED`, and an empty value list reuses the always-false branch.
- **`NULLS FIRST` / `NULLS LAST`.** `orderBy(column, { direction, nulls })` emits the native clause on PostgreSQL, CockroachDB, and SQLite. MySQL and MariaDB have no such clause, and SQL Server only gained one in 2022, so those dialects sort a leading `IS NULL` key instead (a `CASE` expression on SQL Server, which has no bare boolean), which produces the same order on every supported version. A cursor-paginated query rejects it with `ORDER_BY_NULLS_WITH_CURSOR_NOT_SUPPORTED`, because a cursor needs a total order it can resume from.
- **Bindings on `joinRaw` and the five `*JoinRaw` variants.** Raw join fragments take a bindings array now, numbered continuously with the rest of the query.
- **Derived-table joins.** `leftJoin(cb, alias, "alias.col", "t.col")` and the other join forms take a subquery callback in place of a table name, rendering `JOIN (SELECT ...) AS alias ON ...`. The ON columns still have to be written as `table.column`, and an empty alias throws `MISSING_ALIAS_FOR_SUBQUERY`.
- **Outer-join aliases.** `leftOuterJoin`, `rightOuterJoin`, and `fullOuterJoin` delegate to their shorter spellings.
- **Column-to-column, `EXISTS`, and JSON conditions in a join `ON` clause.** The join callback covers the conditions a single column pair cannot express. `whereColumn` compares one column to another, with or without an explicit operator, alongside the `and`/`or` and negated variants; the six `whereExists`/`whereNotExists` forms add a subquery; and the nine JSON behaviours of the `where` builder are available inside `ON` as well, with the same dialect restrictions they carry in a `WHERE`. The conditions compile through the same where interpreter, so their bindings keep counting continuously from the position the join renders at. Write both sides as `table.column` when the joined table is aliased or derived, since there is no model to fall back on.
- **`AS MATERIALIZED` on SQLite.** `withMaterialized` now works on SQLite 3.35 and up as well as PostgreSQL and CockroachDB. `withNotMaterialized` stays as it was, since SQLite has no `AS NOT MATERIALIZED`.
- **`modify(cb, ...args)`.** Applies a reusable query scope, forwarding any extra arguments to it.
- **`value(column)`.** Resolves to a single column of the first row, or `undefined` when there is no row, instead of fetching the rows and indexing them in application code. On a raw query builder a narrowed `select` also narrows the column `value` accepts.
- **`{ skipBinding }` on `limit` and `offset`.** Inlines the value in the SQL rather than sending it as a parameter. Some planners pick a worse plan for a parameterized `LIMIT`, and MSSQL's `TOP`/`OFFSET` handling shifts every later parameter index for a value that never needs to be one. Every other binding in the statement keeps its position.
- **Set-operation wrapping.** `union`, `unionAll`, `intersect`, and `except` accept `{ wrap: true }`, which parenthesizes that branch, so a branch carrying its own `ORDER BY` or `LIMIT` stays scoped to itself.
- **`from(table, { only: true })` on PostgreSQL.** Renders `FROM ONLY <table>`, skipping rows of tables that inherit from it. The other dialects throw `ONLY_NOT_SUPPORTED`.
- **`.queryContext(ctx)` and `.debug()`.** `queryContext` attaches extra fields to the context handed to observers, on top of the `sql`, `params`, `id`, `operation`, and `timestamp` the runner fills in and always owns. `debug()` logs a single query when the data source has logging off, and `debug(false)` silences one query on a data source that logs everything.
- **`onPoolError(error, context)`.** Called when a pooled connection fails while it sits idle, which is a failure with no query to attach it to. The driver has already removed the client from the pool by the time the handler runs, so it reports rather than recovers, and the remaining clients are untouched. A handler that throws is caught and logged instead of reaching the process. With no handler the error is logged and the pool keeps serving, which is the previous behaviour. Only the node `pg` driver reports at the pool level; MySQL, MariaDB, MSSQL, and SQLite surface connection failures on the query that hit them, so the handler never fires there.

### Bug fixes

- **A read inside a transaction could be served by a read replica.** With `replication.slaves` configured, a transaction clone re-created the slave list but never connected it, and every read preferred a slave. In the default configuration that read failed with `CONNECTION_NOT_ESTABLISHED`; under `lazyLoad` it opened a replica on its own connection and returned committed data, so the transaction could not read its own uncommitted writes. A transaction now reads through its own connection, which also means an explicit `setReplicationMode("slave")` no longer overrides that inside a transaction.
- **A failed `commit()` or `rollback()` handed a poisoned connection back to the pool.** The client was released without an error, so the next query inherited a session whose state was unknown. On PostgreSQL that surfaces as `current transaction is aborted` on an unrelated query. The `releaseConnection` contract now carries the failure: `pg` passes it to `release(err)`, which destroys the client, and `mysql2` destroys the connection. MSSQL, the Bun SQL client, and the SQLite family cannot discard a connection, so they are unchanged.
- **A failed `BEGIN` stranded its reserved connection.** The connection was taken from the pool and the transaction started outside any `try`, so a failing `BEGIN` leaked the client, and `startGlobalTransaction` additionally left `isInGlobalTransaction` reporting a live transaction. Both now release the connection on failure, and the global slot is cleared. The release is passed the error, so the client is discarded rather than returned: on PostgreSQL `BEGIN` runs before `SET TRANSACTION ISOLATION LEVEL`, which means a rejected isolation level fails with a transaction already open.
- **`connectionPolicies.retry` never retried anything.** The retry helper returned the adapter promise without awaiting it, so a rejection settled after the frame had left the `try` and the `catch` never saw it. Only a synchronous throw could have been retried, which no adapter does. The policy is unchanged otherwise: only `ECONNREFUSED` is retried, because that fails before the statement reaches the server and a replay cannot double-apply, whereas a reset or a timeout may arrive after the statement has run.
- **Observers saw nothing from inside a transaction, and `onQueryError` never fired.** A transaction runs on a clone of the data source, and the clone did not inherit the observer chain, so every observer registered with `addObserver` was skipped for transactional work. The chain is now shared, which also means the transaction's own `BEGIN`, `COMMIT`, `ROLLBACK`, and savepoint statements reach observers, with `operation: "OTHER"`. Separately, `ObserverChain.notifyError` was defined and documented but called from nowhere, so `onQueryError` was dead; it is now invoked on a failed query, and a throwing observer is reported instead of being discarded in silence, in all three phases.
- **`useCache` wrote to the shared cache from inside a transaction.** A value computed under a transaction's view, including rows it had not committed, was stored in a cache shared with every other caller and survived a rollback. A miss inside a transaction is now computed and returned but not written back, on commit or on rollback. Reads are unaffected, so a value cached before the transaction is still served inside it.
- **A transaction teardown closed the shared cache adapter.** On the SQLite path a transaction clone owns its pool, so its `disconnect()` reached the cache adapter and closed it, which for a `RedisCacheAdapter` meant quitting the process-wide client while other data sources were still using it. Only the instance the adapter was handed to closes it now; a clone's teardown does not.
- **`RedisCacheAdapter.disconnect()` left the closed client in place.** The next call reused the quit client instead of reconnecting, and a second `disconnect()` went to `quit()` on a dead connection. The client is cleared before quitting, so the adapter reconnects on next use and a repeated `disconnect()` is a no-op.
- **`stream()` under `lazyLoad` threw instead of connecting.** `execSqlStreaming` never called `ensureConnected`, so a lazy data source whose first operation was a stream raised `CONNECTION_NOT_ESTABLISHED`. It connects now, mirroring `execSql`.
- **A rollback failure replaced the error your callback threw.** In the callback form, a rejecting `rollback()` propagated before the callback's own error was rethrown, so the caller saw the rollback failure. The callback's error is thrown regardless, with the rollback failure logged.
- **A throwing release left the transaction reporting itself active.** `isActive` was cleared after `releaseConnection`, so a release that threw skipped it and the transaction claimed to still be running with its connection already returned. The flag is cleared first.
- **SQLite connect failures were uncaught, and a good path could hang.** The adapter passed an explicit `undefined` as the driver's mode argument, and node-sqlite3 drops its open callback entirely in that case, which made the adapter's error check unreachable and turned an open failure into an uncaught `'error'` event. The argument is omitted when there is no mode, the database is opened in `createPool()` and awaited, so a bad path now rejects `connect()` and its cleanup runs, and an `'error'` listener covers a later runtime failure.
- **Two concurrent `connect()` calls built two pools.** Both passed the `isConnected` check, and the second assignment dropped the first with its sockets still open. A second `connect()` now rejects while one is in flight, the same error it already raised for an established connection. `ensureConnected` keeps joining an in-flight attempt.
- **An abandoned pg stream kept its pooled client.** A consumer that stopped reading, which is what `for await (...) { break }` does, released the client only when the query finished on its own, unbounded for a long query. Abandoning the stream now destroys the query and releases the client. On a transaction connection it destroys the query but leaves the connection alone, since an abandoned query would otherwise still be running when the transaction issues its next statement.
- **MSSQL transactions were never released.** A transaction that was not committed or rolled back kept its pooled connection, and a failed `commit()` or `rollback()` reached that path too, which showed up as an unrelated query blocking on a row lock until it timed out. A transaction that is still pending when it is released is now ended. Because MSSQL exposes no second lever once `rollback()` itself has failed, the recovery ends the transaction with `IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION` rather than through the method that just failed.
- **A pool built before a slave failed was left to the garbage collector.** The cleanup nulled the references without closing anything, on the reasoning that the GC would release the handles, which is not true of an open socket. A pool that was already built, on the master or on a slave, is now closed best-effort, bounded so a pool caught mid-construction cannot hang a path that is already failing.
- **A nested transaction silently swallowed a requested isolation level.** An isolation level passed to a nested call had no effect, since a savepoint keeps the outer transaction's level, but nothing said so. It is now reported with `logger.warn`, and the request is still inherited.
- **`insertMany` with a single row and `returning` resolved to an object instead of an array.** The serializer collapses a one-row result to the row itself, and the non-conflict path returned that value under an array type, so a caller doing `.map` or `.length` on the result of `insertMany([row], { returning: [...] })` broke. It showed up as a lost row in `batchInsert`, whose last chunk is often a single row. That path normalizes the shape now, the same way the conflict path already did for `upsertMany`.
- **`whereILike` emitted `ILIKE` on dialects that reject it.** MySQL, MariaDB, SQLite, and MSSQL have no `ILIKE`, so the predicate was a syntax error there. Those dialects now compare `LOWER(column) LIKE LOWER(value)`, which is equivalent for the pattern forms the operator accepts. PostgreSQL and CockroachDB keep the native operator. One placeholder is still emitted, so binding counts are unchanged.
- **`whereNotIn` on a tuple rendered `NOT IN` for a column it was comparing as a group.** It now negates the group, `NOT (("a", "b") IN (($1, $2)))`, matching the positive form.
- **MSSQL row locks were a no-op.** `lockForUpdate()`, `forShare()`, `forNoKeyUpdate()`, and `forKeyShare()` emitted nothing on MSSQL: the table-hint builder switched on uppercase labels such as `"UPDATE"` while `LockType` holds `for_update` and `for_share`, so no branch ever matched and the lock interpreter returned an empty string. A locked MSSQL query now carries `with (UPDLOCK)` or `with (HOLDLOCK)`, with `READPAST` and `NOWAIT` added by the matching options.
- **`ALTER TABLE ... ADD PRIMARY KEY` on SQLite died with "Interpreter not found for sqlite add primary key".** SQLite cannot add a primary key to an existing table, so `Schema::addPrimaryKey` throws `SQLITE_NOT_SUPPORTED` with that message instead of failing inside the parser.
- **`using()` silently dropped the conditions on the join it applied to.** The interpreters render `USING` in place of the `ON` clause and return before reaching the additional conditions, so a join carrying conditions from the callback lost every one of them. `using()` now throws `USING_CONFLICTS_WITH_ON_CONDITIONS` once the last join has conditions.
- **An ON-callback condition on a second join was numbered from the start of the query.** Its placeholders were counted from zero instead of from the position the join actually renders at, so joining twice with a bound ON condition on the second join produced misaligned parameters.
- **`merge()` with nothing left to update rendered an empty `DO UPDATE SET`.** When the only inserted column was the conflict target, the clause was emitted with no assignments, which is invalid SQL on every dialect. It now throws `MERGE_REQUIRES_COLUMNS`, which points at the call site instead of the database, and `ignore()` remains the way to leave the existing row alone.

## [12.3.0] - 2026-10-07

### Features

- **Chainable `onConflict()` on `insert` and `insertMany`.** `insert(row).onConflict("email").merge()` updates every inserted column except the conflict target when the row already exists, `merge(["name"])` narrows that to an explicit list, and `onConflict(...).ignore()` leaves the existing row untouched. It works on both `sql.from(Model)` and `sql.from("table")`, on `insertMany` as well as `insert`, and the conflict target takes a column, a column array, or a `table.column` key (the qualifier is stripped, because PostgreSQL and SQLite reject table-qualified conflict targets). Each dialect renders its own form: `ON CONFLICT ... DO UPDATE SET` on PostgreSQL and CockroachDB, `ON CONFLICT ... DO UPDATE SET ... EXCLUDED` on SQLite, `ON DUPLICATE KEY UPDATE` on MySQL and MariaDB, and MSSQL routes to the same hand-built `MERGE` that `upsert` uses. `returning` is honored on the conflict path, and is emitted after the conflict clause on the dialects that require that order. `.merge()` or `.ignore()` without a preceding `.onConflict()` throws `MERGE_REQUIRES_ON_CONFLICT`, an `.onConflict()` with no following action throws `ON_CONFLICT_REQUIRES_MERGE_OR_IGNORE` when the operation runs, and an empty column list throws `ON_CONFLICT_COLUMNS_REQUIRED`.
- **CTEs on write statements.** `with()` (plus its recursive, materialized, and non-materialized variants) now applies to `insert`, `insertMany`, `insertFrom`, `update`, `delete`, and `softDelete`, not only to `SELECT`. Every dialect except MySQL and MariaDB renders the CTE ahead of the statement. MySQL and MariaDB accept a CTE only in front of a `SELECT`, so a values insert that carries one throws `CTE_NOT_SUPPORTED_ON_INSERT`, an `INSERT ... SELECT` renders the CTE inline after the column list, and `WITH ... UPDATE` / `DELETE` throws `CTE_NOT_SUPPORTED_ON_WRITE` on MariaDB. A CTE's bindings are numbered before the values of the statement it feeds. `truncate` rejects a CTE with `CTE_NOT_SUPPORTED_ON_TRUNCATE`, and `with(alias, columns, cb)` binds an explicit CTE column list.
- **`insertFrom()`.** `sql.from(target).insertFrom(source)` inserts the rows a `SELECT` produces, where `source` is a builder or a callback that builds one. An optional leading column array maps the selected columns to destination columns by name; without it they map positionally, so the source has to list every destination column in table order. It returns the same conflict-aware operation as `insert`, so `onConflict(...).merge()` and `.ignore()` chain onto it. No validation, hooks, or `autoCreate` columns run, because the rows come from the database.
- **`truncate(options)`.** PostgreSQL and CockroachDB accept `{ restartIdentity: true }` (`RESTART IDENTITY`), `{ continueIdentity: true }` (`CONTINUE IDENTITY`), and `{ cascade: true }` (`CASCADE`). Every other dialect throws `TRUNCATE_OPTION_NOT_SUPPORTED` when an option is set, and CockroachDB rejects the two identity options because its `TRUNCATE` grammar carries only `CASCADE`/`RESTRICT`. SQLite keeps its `DELETE FROM` fallback.
- **Target-less `onConflict()`.** Calling `onConflict()` with no column covers the "do nothing" case without naming the unique constraint. PostgreSQL, CockroachDB, and SQLite render `ON CONFLICT DO NOTHING`, MySQL and MariaDB turn the statement into `INSERT IGNORE`, and MSSQL throws `NOT_SUPPORTED_IN_MSSQL`. A target-less `merge()` still throws `MERGE_REQUIRES_ON_CONFLICT`.
- **Empty inserts and raw set-operation bindings.** `insert({})` renders `DEFAULT VALUES` on PostgreSQL, SQLite, and MSSQL and `() VALUES ()` on MySQL and MariaDB. `union`, `unionAll`, `intersect`, and `except` accept a bindings array alongside the raw SQL string.
- **Expression nodes as model write values.** `sql.from(Model).insert(...)`, `insertMany(...)`, and `update(...)` accept `sql.rawStatement("upper(name)")` and the JSON mutation helpers (`sql.jsonSet`, `sql.jsonInsert`, `sql.jsonRemove`) wherever a column value goes, so a write can compute a value in the database without casting the payload to `any`. Raw statements are accepted on any column, while the JSON mutation helpers are typed to JSON columns (`col.json()` and `col.jsonb<T>()`) because they write a path rather than a value. The interpreters already rendered these nodes inside records; the model-level data types were the only thing rejecting them.

### Bug fixes

- **A model-level upsert preview omitted its conflict clause.** `sql.from(User).upsert(...).toSql()` and `.toQuery()` rendered only the `INSERT` and dropped the `ON CONFLICT`/`ON DUPLICATE KEY` half that the execution path appended, so the preview did not match the statement that actually ran. Both now include it, matching what `sql.from("table").upsert(...)` already showed.
- **A raw `upsert()` dropped search-criteria columns that were absent from the data.** The preview inserted `{ ...searchCriteria, ...data }` while execution inserted only the keys of `data`, so a criteria-only column showed up in `toSql()` but not in the running statement. Both now use the merged object.
- **`upsertMany` with a single row and `returning` resolved to an object instead of an array on PostgreSQL and CockroachDB.** The serializer collapses a one-row result to the row itself, and the conflict path returned that value under an array type (the model-level `upsert` guarded against it, `upsertMany` did not), so callers doing `.map` or `.length` on the result of `upsertMany(..., [row], { returning: [...] })` broke. The conflict path normalizes the shape now, so a one-row `upsertMany` resolves to an array and the same holds for `insert().onConflict()` with `returning`.
- **MSSQL logged a spurious `on_duplicate` warning on the raw `upsert()` path**, because that path fed a conflict node to the no-op MSSQL interpreter even though the real write is a `MERGE`. The path now routes to `MERGE` without emitting the warning.
- **A write silently dropped clauses it could not express, and its preview could disagree with what ran.** Clause state a write cannot express (a `SELECT` list, `DISTINCT`, `GROUP BY`, `HAVING`, a set operation, a row lock, a comment or hint, a join, an `ORDER BY`/`LIMIT` outside MySQL, an `OFFSET`) was discarded without error, so `select("id").where(...).delete()` ran as though the `select` were never written and `innerJoin(...).update(...)` emitted `UPDATE ... INNER JOIN` SQL that most dialects reject. The `toSql()`/`toQuery()` preview also built its node list on a path separate from execution, so the two could diverge. Both now go through one node list, and the unusable clauses throw at the builder call: `SELECT_ONLY_CLAUSE_ON_WRITE`, `JOIN_NOT_SUPPORTED_ON_WRITE`, and `ORDER_BY_LIMIT_NOT_SUPPORTED_ON_WRITE`. MySQL's `DELETE ... LIMIT` and `UPDATE ... ORDER BY` keep working. An `update({})` with no columns now throws `UPDATE_REQUIRES_COLUMNS` instead of emitting an empty `SET`.
- **Chaining `onConflict()` onto `insertFrom()` dropped the source `SELECT` and its target column list.** The conflict-clause rebuild constructed a fresh insert node without the `source` and `targetColumns` the operation started with, so MySQL rejected the statement with "Column count doesn't match value count at row 1". Both are carried over now.

## [12.2.2] - 2026-10-05

### Bug fixes

- **User-authored SELECT output names are no longer rewritten to model property names.** `selectRaw("id as user_id")` returned `{ userId }` instead of `{ user_id }` whenever the output name matched another column's database name. Model SELECTs are aliased to model property names before they run, but raw statements and tuple aliases are left untouched, so the result key missed the property-name lookup and hit the db-name fallback meant for joined tables. The query builder now records the output names the user authored (raw statements in aliased or bare form, tuple aliases, and the aliases passed to `selectFunc`, window, distinct-aggregate and JSON select helpers) and the serializer returns those keys verbatim, including alongside `SELECT *`.

## [12.2.1] - 2026-10-04

### Bug fixes

- **Window-function and distinct-aggregate aliases were not typed on the query result.** `rank`, `denseRank`, and `rowNumber`, plus `countDistinct`, `sumDistinct`, and `avgDistinct`, only existed on the base select builder, so passing an alias never added that property to the inferred result of `.one()`/`.many()`; the result stayed the full model type. They are now overridden on both `sql.from(Model)` and `sql.from("table")` builders, mapping the alias to `number`. `countDistinct`, `sumDistinct`, and `avgDistinct` now require the alias (it was optional), since an unaliased result cannot be typed; `rank`, `denseRank`, and `rowNumber` still accept an optional alias and leave the result type unchanged when it is omitted.

## [12.2.0] - 2026-10-03

### Features

- **CTE, set-operation, and join parity on the query builder.** `withSchema(schema)` qualifies a CTE, `withNotMaterialized(alias, cb)` emits `AS NOT MATERIALIZED` (Postgres/CockroachDB), `using(...columns)` renders `USING (...)` on `join`/`innerJoin`/`leftJoin`/`rightJoin` (plus bare-`join` overloads) and is rejected on MSSQL, `fromRaw(raw, bindings?)` builds a raw `FROM` (also `sql.fromRaw`), `intersect`/`except` join set operations, and `crossJoin(table, alias?)` adds a `cross join`.
- **Negated-column and extended JSON predicates.** `whereNotColumn` (plus `andWhereNotColumn`/`orWhereNotColumn`); `whereJsonObject`/`whereNotJsonObject`, `whereJsonPath`, `whereJsonSupersetOf`/`whereJsonSubsetOf`, and `whereJsonHasNone`, each with `and`/`or` variants; and `columnInfo([column])` for query-time column metadata.
- **Extended HAVING helpers.** `havingNull`/`havingNotNull`, `havingIn`/`havingNotIn` (array or subquery), `havingBetween`/`havingNotBetween`, `havingExists`/`havingNotExists`, and `havingWrapped`, each with its `and`/`or` variant.
- **JSON mutation in `update()`.** `sql.jsonSet`, `sql.jsonInsert`, and `sql.jsonRemove` build an expression that mutates a JSON column at a `'$.a.b'` path or segment array. `jsonSet` works on every dialect; `jsonInsert` and `jsonRemove` work on PostgreSQL, MySQL/MariaDB, and SQLite, while MSSQL supports only `jsonSet` (`JSON_MODIFY`).
- **Postgres lock strengths.** `forNoKeyUpdate()` and `forKeyShare()` add the two weaker row locks, both accepting `{ skipLocked, noWait }`; they throw `LOCK_STRENGTH_NOT_SUPPORTED_IN_*` outside PostgreSQL.
- **Per-query timeout.** `timeout(ms, { cancel })` rejects with a `QUERY_TIMEOUT` `HysteriaError` once the limit is exceeded. With `cancel: true`, PostgreSQL cancels through `pg_cancel_backend`, MySQL/MariaDB through `KILL QUERY`, and MSSQL through `Request.cancel()`; SQLite and Bun only enforce the wall-clock timeout.
- **Window functions and distinct aggregates.** `rank(alias, { partitionBy, orderBy })`, `denseRank(...)`, and `rowNumber(...)` add `OVER (...)` window calls with an optional `PARTITION BY` and `ORDER BY`; `partitionBy` takes a column or array, `orderBy` a column, `{ column, order }`, or an array of either. `countDistinct`, `sumDistinct`, and `avgDistinct` add `COUNT/SUM/AVG(DISTINCT column)` to the select list. Both are select-list additions available on every dialect. `clearCounters` is intentionally not provided: Hysteria has no deferred `increment`/`decrement` (counter updates are immediate writes), so there are no pending counters to reset.

### Bug fixes

- **`generate:migrations` no longer nulls the DB default on an `autoCreate` timestamp.** A column declared `col.datetime({ autoCreate: true })` gets `default current_timestamp` from the DDL emitter and is omitted from INSERT by the ORM, but the model records `autoCreate`, not `constraints.default`. The differ read that as model-has-none / db-has-one and emitted `alterColumn((col) => col.datetime("created_at").default(null).notNullable())`, which deletes the default; the next insert then failed with a NOT NULL violation. The raw (`-o raw`) path had the same defect with no destructive marker. The "is this DB default drift?" rule was implemented twice with different answers: `getDefaultChange` used its own inline checks while the raw-SQL generator used the shared `schema_diff_defaults` helpers, and the code generator used neither. Both now consult the shared helpers, so an implicit `autoCreate` timestamp (and an implicit auto-increment sequence/rowid) is not treated as drift and no longer produces a modify operation at all. Genuine default add/drop for explicit `constraints.default` columns is unchanged.

- **HAVING clauses were joined without a separator.** `HavingNode` chained with a trailing space, so two conditions rendered as `... $2or  "x"`; it now uses a leading space like `WHERE`.
- **MySQL/SQLite HAVING emitted Postgres-style `$n` placeholders.** Any HAVING condition with a bound value produced invalid SQL on those dialects; placeholders are now dialect-correct (`?`).
- **Update `SET` parameter numbering is now sequential.** The update interpreters numbered placeholders by column index, which misaligned once an expression value contributed its own bindings; values are numbered as they are bound, and expression nodes (SQL functions, JSON mutations) render in place with their bindings.
- **MSSQL ignored `isNegated` on raw-column WHERE predicates.** Negated raw-column conditions now wrap the predicate in `not (...)`.
- **MySQL and MariaDB disagreed on JSON object equality.** Structural equality is emitted per dialect (`CAST(? AS JSON)` on MySQL, plain text on MariaDB).

## [12.1.0] - 2026-10-03

### Features

- **Dialect-typed SQL comments and optimizer hints on the query builder.** `comment(comment)` prepends a native SQL comment before `SELECT` and `hintComment(hint)` emits an optimizer hint (`/*+ ... */`) immediately after the `SELECT` keyword, where MySQL and Oracle read it. Both are available on `sql.from("table")` and `sql.from(Model)`, select-only, and stackable (repeated `hintComment()` calls merge into a single hint comment, matching Knex); they survive `clone()` and are cleared with `clearComment()` / `clearHintComment()`. The argument is the comment literal as it appears in SQL — `-- line`, `/* block */`, plus `# line` and `/*! executable */` on MySQL/MariaDB — and is type-checked against the active dialect: `#` comments and `/*+ */` hints are compile errors on PostgreSQL/SQLite/MSSQL. This required threading the dialect generic through the query builder’s `select()`/`from()` chain. Line comments are terminated with a newline so they cannot comment out the rest of the statement. A value that could escape the comment (a newline inside a line comment, a nested `*/` in a block comment) or contains `?` is rejected with `INVALID_SQL_COMMENT`. Note that `/*+ ... */` is only an optimizer hint on MySQL/Oracle; PostgreSQL reads it only with the `pg_hint_plan` extension, SQLite ignores it, and MSSQL uses `OPTION (...)`, so on those dialects it is a plain comment.

## [12.0.2] - 2026-09-19

### Bug fixes

- **jsonb values written through the Bun driver were double-encoded.** A column's `prepare` returns the payload as a JSON string, which node `pg` coerces into `jsonb` but `Bun.sql` binds as a JSON _string_, storing `"{\"sandbox\":true}"` rather than the object. Reads still worked (the column's `serialize` re-parses), so the defect was silent, but `->>` returned `NULL` on the column, which broke SQL-side filters over it. A string payload bound to a `jsonb` column now emits `::text::jsonb`, parsing the text into the document; the bare `::jsonb` used for object payloads is a no-op on an already-string value. Applies to `insert` and `update` on `postgres` and `cockroachdb`.
- **`acquireLock`/`releaseLock` leaked the lock when a transaction ran between them.** `pg_try_advisory_lock` is session-scoped, but both calls went through the pool, so under Bun.sql — where a transaction rotates the pooled connection — the unlock ran on a different backend and the lock stayed held, making every later `acquireLock` for that key return `false` for the life of the process. Locks now share one dedicated reserved session from acquire to release; it is returned to the pool once the last key is unlocked, and released on `disconnect()` if the caller never unlocks.

## [12.0.1] - 2026-09-18

### Features

- **`sqlFunc` tokens in `where()` and `having()`.** A symbolic token can now stand in as the right-hand side of a predicate and renders inline instead of being bound as a parameter: `where("created_at", "<", sqlFunc.now())`. Previously the `SqlFuncNode` was handed to the driver as a bound value, producing a driver error or `[object Object]`.
- **Custom `sqlFunc` tokens.** `registerSqlFuncRenderer(dialect, renderer)` (also exported as the `SqlFuncRenderer` type) registers a renderer for a dialect, or for every dialect via `"*"`. A renderer returns `undefined` to fall through to the next one, then to the built-in tokens; an unregistered function name renders as `fn(args)`.
- **`coerceNumericTypes` input option.** Opt-in, `postgres`/`cockroachdb` only, off by default. When enabled the `pg` driver parses `int8` to a real `bigint` and `numeric` to a `number` instead of the strings it returns today, which matters on result paths that bypass a model column's `serialize` (`rawQuery`, `sql.from("table")`, `selectRaw` aliases, generic `col<T>()`). Enabling it is breaking for callers comparing against strings. A caller-supplied `driverOptions.types` takes precedence. The Bun driver ignores the flag.

### Bug fixes

- **MySQL/MariaDB uuid columns get a native DDL default.** `create table` now emits `varchar(36) default (uuid())`, so rows inserted outside the ORM (raw SQL, another service, a data migration) receive a generated UUID instead of `NULL`. Foreign-key uuid columns are excluded, since a random FK value would violate the constraint. On MySQL the default is stripped from `alter table ... add column`, which the server rejects with ERROR 1674 (unsafe under binlog, including with `binlog_format=ROW` and `log_bin_trust_function_creators=ON`); MariaDB accepts it on both paths. Values for rows inserted through the ORM continue to be generated by `prepare`, on every dialect.
- **`col.datetime({ autoUpdate: true })` works again on the model path.** 12.0.0 dropped the `autoUpdateColumns` list when it removed the auto-column machinery, which left the flag inert: nothing added the column to an UPDATE payload, so `updated_at` stayed frozen at its insert value. The flag behaves as documented — `prepare` runs on every update regardless of whether the caller supplied the value, so an explicitly passed value is regenerated rather than preserved.
- **`autoCreate: true` no longer generates a destructive migration.** The differ compared only `constraints.default`, but the model records an auto-generated timestamp as `autoCreate` (the date column options omit `default`), so it read the column as model-has-none/db-has-one and emitted `drop default`. `db:generate` therefore produced a migration that converged on a re-run while leaving every insert failing with a NOT NULL violation, because the ORM still omits the column on insert. Implicit timestamp and auto-increment defaults (PostgreSQL `nextval`, CockroachDB `unique_rowid`) are now recognised and left alone.
- **`bun-sql` errors expose the Postgres SQLSTATE on `.code`.** Bun wraps server errors and moves the SQLSTATE into `.errno`, so consumers branching on `error.code === "23505"` behaved differently under the default Bun driver than under the node drivers, despite the adapter canonicalizing result shapes. The SQLSTATE is now also set on `.code`, with the original error preserved as `.cause`; Bun's own codes are left untouched. MySQL/MariaDB report a numeric `errno` (1062 for a duplicate key) rather than a SQLSTATE, so those are unchanged — `mysql2` reports the symbolic `ER_DUP_ENTRY` there and matching it would need a server-error-number table.
- **`t.increment("id").primaryKey()` works on SQLite.** The column interpreter already emits `integer primary key autoincrement` inline, and the builder also emitted a table-level primary key constraint, so the CREATE failed with `table "x" has more than one primary key`. The table-level constraint is now skipped when the column carries the key inline.
- **SQLite stores dates as datetimes, not epoch milliseconds.** SQLite has no date type — the column is TEXT and the value is stored as written — and neither `node-sqlite3` nor `bun:sqlite` can bind a `Date`. A `Date` reaching the driver was therefore coerced to epoch milliseconds (`1577934245000.0`), which the read path could not parse, so the model received an `Invalid Date` and ordering or comparison silently broke. Date values are now formatted to the same representation the database writes for an `autoCreate` column (`default current_timestamp`) before being bound. Other dialects bind `Date` natively and are unaffected.
- **`getSum`/`getMax`/`getMin`/`getAvg` resolve model property names.** They built their clause with `selectRaw`, which interpolates the argument verbatim, so a model property whose database column differs (`userId` → `user_id`) reached SQL untranslated and the query failed with `no such column`. They now use the same rendering path as `selectFunc()`, so the column is resolved through the model's column map and quoted per dialect. Note `getSum("*")` is not meaningful in any dialect (`sum(*)` is invalid SQL) — pass a column.
- **MariaDB keeps its dialect identity inside `alter table`.** The MySQL alter-table interpreter parsed its children with a hardcoded `"mysql"` dialect, so nested interpreters could not tell MariaDB apart from MySQL and made MySQL-only decisions for both.

### Documentation

- Corrected the `sqlFunc` per-dialect table (MySQL/MariaDB render `(uuid())`; MSSQL `now()` renders `current_timestamp`), replaced the documented `.update().set({...}).execute()` example — neither method exists, the API is `update(data, returning?)` — and documented predicate usage, custom tokens, and the MySQL `alter table` uuid limitation.

## [12.0.0] - 2026-09-18

### Breaking changes

- **Hooks removed.** `afterFetch`, `beforeInsert`, `beforeInsertMany`, `beforeUpdate`, and `beforeDelete` no longer exist. Only `beforeFetch` remains (mutates the query builder once per query, still async-capable). The `ignoreHooks`, `ignoreBeforeUpdateHook`, and `ignoreBeforeDeleteHook` options are gone.
  - Write-time defaults now live in the database: UUID and datetime columns get native DDL defaults (`gen_random_uuid()`, `DEFAULT (UUID())`, `NEWID()`, `lower(hex(randomblob(16)))`, `NOW()`/`CURRENT_TIMESTAMP`).
  - Query-result transforms that used `afterFetch` must move to application code after `many()`/`one()`.
- **Oracle support removed.** The `oracledb` driver, interpreter, `handleOracleIdentityInsert`, and CLI/docker-compose integration are deleted. Supported dialects: postgres, mysql, mariadb, sqlite, mssql, cockroachdb.
- **`many()`/`stream()` result serialization is now synchronous.** No per-row `Promise.all` or async lifecycle callbacks; rows are shallow-copied onto the model prototype with aliased column names.
- **`serialize`/`prepare` are synchronous.** A `serialize` that returns a Promise now throws.
- **`autoInsertColumns`/`autoUpdateColumns` machinery removed.** Casing is applied via `SELECT ... AS` aliases; no per-query column re-fill.
- **Min DB versions bumped:** PostgreSQL 13+, MySQL 8.0.13+, MariaDB 10.5+, SQLite 3.35+, MSSQL 2019+.
- **Driver resolution no longer falls back across environments.** A dialect with no driver for the resolved runtime now throws `DriverNotFoundError` instead of quietly resolving to the Node factory — e.g. `jsEnvironment: "web"` with `type: "postgres"` used to boot a Node `pg` pool that could never have worked in a browser. The fallback is kept only for `bun` → `node`, which is legitimate (there is no Bun-native `mssql`).
- **`ResolvedJsEnvironment` gains `"react-native"`.** Consumer code doing an exhaustive `switch` over the environment that ends in `const _never: never = env` no longer compiles until the new member is handled.

### Features

- **Web and React Native SQLite drivers.** `jsEnvironment: "web"` resolves to `@sqlite.org/sqlite-wasm` and `"react-native"` to `@op-engineering/op-sqlite`, both optional peer dependencies loaded lazily so Node and Bun bundles never pull them in. Neither path touches a Node API. Browser SQLite is in-memory for `:memory:` and OPFS-backed for any other name (requires a dedicated worker plus COOP/COEP headers); React Native opens a real file. See [Web & React Native Drivers](website/docs/databases/sql/web-and-react-native-drivers.md).
- **Type-safe `driver` prop.** A registered name is now a union narrowed by `(dialect, jsEnvironment)` — postgres on Node offers `pg`, postgres on Bun offers `bun-sql`, and a pair with no builtin offers nothing. Omitting `jsEnvironment` resolves against the Node names, so existing configs keep compiling. A `(string & {})` hatch keeps names registered through `registerDriverAdapter` assignable; unknown names are caught at runtime by `DriverNotFoundError`.
- **Third-party drivers: pass the factory as `driver`.** `driver` now accepts an inline `DriverAdapterFactory` alongside the name form, so `driver: { name, dialects, create }` is the custom path — no `"custom"` sentinel, no separate option to keep in sync. The factory declares the dialects it serves, builds the adapter per datasource (clones and replicas each get their own), and skips environment filtering since passing one is already an explicit opt-in. A declared-dialect mismatch names both sides in the error, and an object that is not a factory is rejected with a message instead of a `TypeError`.
- **Worker runtimes are detected as `"web"`.** A Web or Service Worker has no `window`, `document`, or `process`, so it previously resolved to `"node"` and crashed at import time dereferencing `process.env`. `NodePlatformAdapter.readEnv` is also guarded now. React Native crypto degrades from `randomUUID` to a `getRandomValues`-built v4 UUID, and throws an actionable `PlatformUnsupportedError` when neither exists instead of falling back to weak randomness.

- **`sqlFunc` global namespace.** Symbolic expression tokens (`$uuid`, `$now`, `$currentTimestamp`) rendered per-dialect by the interpreter. Available in migration column DDL defaults (`table.<type>(...).default(sqlFunc.uuid())`) and `update().set({ col: sqlFunc.now() })` expression values.
- **`RETURNING` on writes.** Insert/insertMany/update/delete can return generated values across dialects: native `RETURNING` (postgres, cockroachdb, sqlite, mariadb), `OUTPUT inserted.*` (mssql, with `AS` aliases), and follow-up `SELECT` (mysql).
- **DB-generated column defaults on reads.** Columns omitted from INSERT that have database defaults now come back automatically via RETURNING when requested.
